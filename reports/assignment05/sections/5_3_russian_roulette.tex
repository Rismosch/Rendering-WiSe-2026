\item To implement Russian Roulette for the BSDFPathIntegrator, the code remains largely unchanged. For brevity, the unchanged code is hidden under the ellipses \code{\ldots}. In the constructor we read \code{rrMinBounces} from the configuration and initialize it with \code{m\_maxBounces} in case it is missing. In the loop, after the BSDF calculation, we play Russian Roulette, but only if the minimum number of bounces is exceeded. We compute $P$ and the weighted radiance $L_{RR}$. We compute $y$ as the sum of the colors channels (we treat each color dimension as its individual light, which added together return their luminance). If $y$ is below $P$, we weight \texttt{radiance} by $P$. Otherwise we lost the Russian Roulette and exit the loop early. The implementation is seen in Listing \ref{lst:roussian-roulette}.

public:

        m_maxBounces = propList.getInteger("maxBounces", 10);

    }

    Color3f Li(const Scene *scene, Sampler *sampler, const Ray3f &cameraRay) const override {

            ...
            // 2. if emitter, evaluate and add to radiance
            ...
            // 3. compute wi
            ...
            // 4. sample wo and value from bsdf sampler
            ...

            // russian roulette!

                float y = L_RR.x() + L_RR.y() + L_RR.z();
                if (y < P) {
                    radiance /= P;
                } else {
                    break;
                }
            }

        }

\item Having \texttt{m\_maxBounces} is still useful, because Russian Roulette alone does not guarantee that the loop terminates. In a very unlikely scenario, the loop may run indefinitely. Having an upper bound on loops ensures that a loop will end. Tangentially related: See rule 2 of NASAs "The Power of 10: Rules for Developing Safety-Critical Code": 

\begin{quote}
All loops must have a fixed upper-bound. It must be trivially possible for a checking tool to \textit{prove} statically that a preset upper-bound on the number of iterations of a loop cannot be exceeded. If the loop-bound cannot be proven statically, the rule is considered violated. \cite{holzmann2006power}
